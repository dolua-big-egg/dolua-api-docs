# 可用资源

**文档版本** `1.1.0`

本篇汇总 **当前 NT26（含 NT26 PRO）固件** 里，脚本作者能用到的堆、内部代码区、文件个数和调度名额。数字是上限，不是「建议把每项用满」。

查询类接口（堆占用、内部存储用量）见对应模块 API。本篇不列函数签名。

未单独公布的其它型号，不要套用这里的 Flash 总额。

## 1. 两块完全不同的「内存」

| | Lua 堆 | 内部代码 / 文件区 |
| --- | --- | --- |
| 介质 | RAM | Flash（压缩后按实际占盘核算） |
| 干什么 | 运行中的字节码、表、字符串、用户数据 | 入口源码、用户模块源码、内部短文件与字节文件 |
| 当前上限 | **700 KB** / 虚拟机 | **220 KB** 三家共用（见第 4 节） |
| 复位后 | 清零，重建虚拟机 | 还在 |

把 100 KB 源码烧进去，运行时堆占用通常 **大于** 100 KB：还要加编译结果、加载的平台模块、运行中的表。反过来，源码很小但在堆上缓存了大字符串，会先撞堆上限而不是 Flash。

## 2. Lua 堆（RAM）

当前固件给主脚本虚拟机的堆上限是 **700 KB**。

计入这份堆的包括：

- 入口和已 `require` 的用户模块的编译结果
- 平台模块装入后的表与用户数据
- 脚本自己的 table / string / 闭包
- 信箱和队列里尚未取走的编码缓冲（在派发路径上）
- 部分模块为一次编解码申请的临时块（内部对象编码另有单次 RAM 上限，见存储篇）

不计入、或只间接相关的：

- 外挂 NOR 上的文件系统内容（不进这份堆，读时才会拷一段出来）
- 图形模块若单独划了显示堆，按该模块自己的上限，不要和 700 KB 混成一笔

堆不够时，常见是创建虚拟机失败，或运行中分配失败。长期脚本应避免：

- 把大日志、整份 HTTP 正文一直挂在全局表上
- 在热路径上反复拼接超长字符串还不放手
- 同时打开许多带大缓冲的对象

运行中可以查询「已用 / 上限」两个整数，见 [`rt` 的堆查询](../api/module/rt.md)。

## 3. 引擎线程栈

跑虚拟机和调度循环的那条系统线程，栈大约 **80 KB**。这不是给脚本配置的参数，一般也改不了。

普通业务循环、让出、回调投递都不会碰到它。会有压力的情况主要是：Lua 侧极深的同步递归，或一次调用在模块里展开了很大的同步工作且不让出。日常把重活拆到多次让出之间即可。

## 4. 内部代码与文件区（Flash）

NT26 PRO 内部有一块 **220 KB** 的共享配额，三家合用，按 **压缩后实际落盘** 计：

```
脚本区落盘  +  内部对象文件  +  内部字节文件  ≤  220 KB
```

| 占用者 | 存什么 |
| --- | --- |
| 脚本区 | 入口和用户模块（压缩后）。底层按 A/B 两槽设计，**当前未启用切换** |
| 内部对象文件 | 可序列化的 Lua 值（配置表等） |
| 内部字节文件 | 原始字节：日志块、图片、HTTP 下来的文件等 |

要点：

- 本机以用量查询返回的总额为准；上表是当前公布值。
- 底层两槽的文件若都落盘，会一起计数。**当前未启用双槽切换**（空间不够同时留两份完整包），不要按「长期两份脚本」来规划；日后 8+8 / CAT4 若打开切槽，再按接近 2 倍脚本区预留。原因见 [runtime.md 第 2 节](runtime.md#2-脚本副本a--b-两槽)。
- 脚本越大，内部文件能写的就越少。脚本升级变大，可能让原来写得下的文件变成写不下。
- 重复性高的文本压缩比好；已经压过的 JPEG / 固件片往往几乎不缩小。不要按源码字符数或 `#string` 估占盘。
- 外挂 Flash 上的文件系统和 KV **不走** 这 220 KB。

更细的分工见 [存储怎么分](storage.md)。

单份入口、单份用户模块的 **明文** 上限也是 220 KB，但共享配额通常先碰到。明文 220 KB 再压缩仍可能把 220 KB 配额打满。

## 5. 入口文件与用户模块

| 项 | 上限 | 说明 |
| --- | --- | --- |
| 脚本虚拟机 | **1** | 当前只跑一份引导包 |
| 入口脚本 | **1** | 几乎总是工程里的主文件 |
| 用户模块个数 | **35** | 编号 1…35；未登记的打不进包 |
| 模块名 | **最长 31** 字符 | 字母数字、`.`、`_`；与 `require` 名一致，不含 `.lua` |
| 入口明文 | **220 KB** | 与共享配额是两道闸，配额通常更紧 |
| 每个用户模块明文 | **220 KB** | 同上 |
| 清单 JSON | 约 **8 KB** | 描述入口、模块、选项 |
| 版本串 | 约 **31** 字符 | 清单字段 |
| 副本 ID | 约 **47** 字符 | 清单字段 |

模块名合法例子：`led`、`net.client`、`crc16`。空名、超过 31 字符、含斜杠或其它符号会在部署时被拒。

平台预加载模块 **不占** 这 35 个名额。35 只限制你自己的 `.lua`。

内置资源（图片、字库）不是用户模块，走内部文件配额，见工程篇和存储篇。

## 6. 调度与消息名额

摘自运行时调度，便于和本篇其它上限放在一起看。细节与失败文案以 [`rt`](../api/module/rt.md) 为准。

| 项 | 上限 |
| --- | --- |
| 任务协程 | **16**（含入口第一次让出占用的槽） |
| 软件定时器 | **8** |
| 事件队列 | **128** |
| 信箱不同主题 | **124** |
| 每主题的信箱回调 | **8** |
| 队列不同名字 | **124** |
| 单条队列深度 | **1～128** |
| 主题字符串 | **23** 字节 |
| 单条信箱 / 队列编码 | **8192** 字节 |
| 表嵌套 | **10** 层 |
| 表项合计 | **4096** |

虚拟机退出时上述槽位全部释放。没有「用户关闭整个调度器」的接口。

## 8. 下载包体积

配套工具打出来的压缩包，在 USB / 拉取路径上还有一道 **整包约 260 KB** 的接收上限（压缩后的包本身）。这和 220 KB 内部配额、700 KB 堆是三件不同的事：

| 闸门 | 卡的是 |
| --- | --- |
| 整包约 260 KB | 一次传输能不能收完 |
| 共享 220 KB | 解压落盘后脚本 + 内部文件能不能写下 |
| 堆 700 KB | 跑起来之后 |

包里若带大图，即使压缩包勉强能传，落盘也可能超配额。大资源优先放外挂盘。

## 9. 怎么估算会不会超

按这个顺序想，比「源码一共多少行」准：

1. **当前这份脚本压缩后** 占多少？当前未启用双槽切换，不要按两份完整包来留空。日后若打开切槽，再把第二槽算进去。
2. 内部对象 + 内部字节还要留多少？图片、字库算在这里。
3. 跑起来之后，平台模块 + 用户模块字节码 + 业务表，估一估是否靠近 700 KB。图形若另划显示堆，单独算。
4. 任务是不是开太多、定时器是不是开满、回调是不是在往队列里灌大表。

实践建议：

- 用户模块按职责拆，但不要拆成几十个只有几行的文件（每个清单项和压缩记录都有开销，且最多 35 个）。
- 能外挂的大二进制不要塞内部区。
- 不要为尚未启用的第二槽预留一整份脚本配额。
