# 消息和调度

**文档版本** `1.0.0`

DoLua 的「多任务」是 **同一虚拟机里的协作式协程**。同一时刻只有一条 Lua 协程在跑。硬件中断、网络线程可以投递事件，但真正执行脚本回调的是调度循环。

本篇用伪码讲机制。信箱、队列、定时器、让出延时的函数名、超时单位和失败文案见 [`rt`](../api/module/rt.md)；整线程睡眠 / 忙等见 [`sys`](../api/module/sys.md)。

## 1. 先建立这张图

```
硬件 / 协议线程                 脚本引擎线程
──────────────                 ────────────
GPIO 边沿 ──┐
串口收包  ──┤
MQTT 报文 ──┼──► 事件队列 ──► 调度循环 ──► 唤醒某条协程
定时器到期 ─┤                      │         或 调用短回调
信箱投递  ──┘                      │
                                   ▼
                            同一时刻只跑一条 Lua
```

| 角色 | 做什么 |
| --- | --- |
| 任务协程 | 业务循环；可以让出、可以等消息 |
| 短回调 | 在调度循环里同步执行；做完必须马上返回 |
| 事件队列 | 把「发生了某事」从投递方送到循环；有深度上限 |
| 信箱 / 队列 | 脚本自己的消息通道，见第 5 节 |

## 2. 协作，不是抢占

操作系统可以同时跑多条线程。脚本虚拟机里不是这样：

- 一条协程从「得到 CPU」到「主动让出」，中间 **不会** 被另一条 Lua 协程抢走。
- 让出点主要是：延时、等信箱、等队列、以及少数模块提供的「等连接 / 等一包」类接口。
- 两次让出之间的代码天然互斥，一般不必为 Lua 表加锁。
- 漏写让出的死循环会饿死其它任务、定时器和所有 Lua 回调。

```lua
-- 伪码：错误——永不让出
循环:
    计数 = 计数 + 1          -- 调度循环进不来

-- 伪码：正确——周期性把 CPU 还回去
循环:
    干活()
    让出(一段时间)
```

任务槽有上限（当前约 **16** 条，含入口第一次让出占用的那条）。开很多「空转但不让出」的循环，会既占槽又饿死别人。

## 3. 调度循环和事件队列

入口协程第一次让出（或跑完）之后，引擎进入循环：

```lua
-- 伪码
循环:
    事件 = 从队列取出()          -- 没有事件就睡眠，可配合低功耗
    若 事件是 唤醒某协程:
        恢复该协程
    若 事件是 短回调:
        调用回调()               -- 调用期间占用整条调度
    释放事件附带的缓冲
```

投递方（边沿、串口、网络、脚本自己的发送）把事件放进队列就返回。队列深度当前是 **128**。生产快于消费时投递失败，表现为「事件队列满」一类错误。回调里塞很大的表、工作协程迟迟不取消息，都会把它打满。

内部完成事件（某次连接完成、某次挂载完成等）走内部主题，**不会**进脚本自己订阅的信箱。

## 4. 回调在哪执行

外设和网络的「回调」**不在硬件中断里跑 Lua**。路径是：

```
中断或协议线程  →  投递到事件队列  →  调度循环取出  →  调用你的函数
```

因此：

- 回调期间占用调度，其它协程和其它回调都要等它返回。
- 回调必须短：把数据投进信箱或队列，立刻返回。
- 回调里不要让出、不要等消息、不要做同步联网、不要同步发布。
- 先启动「已经卡在等待上」的工作协程，再注册回调，避免头几包没人收。

```lua
-- 伪码：推荐
启动任务:
    循环:
        成功, 数据 = 等待信箱("uart1")
        若 成功: 处理(数据)

注册串口回调:
    投递信箱("uart1", 本次数据)
    立即返回
```

定时器到期、信箱上挂的回调，同样在调度循环里执行，遵守同一条纪律。

图形界面若接入本运行时，刷新和输入事件也走这条循环，不要在回调里做重计算。

## 5. 两种消息：信箱与队列

脚本给自己传数据，有两套通道。名字空间分开，各有名额；不要用同一个字符串两边混用，以免自己看晕。

### 5.1 信箱：按主题广播，不替你积压

```
发送(主题, 值)
    │
    ├─► 当时正在该主题上等待的协程  （每个都收到同一份）
    └─► 该主题上登记的回调
没人听：这条就丢了，不会堆给「以后才 wait 的人」
```

适合：回调 → 工作协程；多处同时想知道「发生了某事」。

主题名是短字符串，当前最长 **23** 字节（还要留结束符）。超长截断后，不同主题可能撞成同一个名字。

### 5.2 队列：先创建，FIFO，一条只给一个等待者

```
创建队列(名字, 深度)
发送(名字, 值)     -- 可以积压，直到满
接收(名字)         -- 只有一个等待者拿走这一条
```

适合：生产者可能突发、消费者要按顺序拉空；一对一交接。

### 5.3 能放什么

两套编码规则相同。逻辑上可发：空值、布尔、数字、字符串（可含零字节）、表（数组或「字符串 / 数字 / 布尔」键的映射）。

不能发：函数、用户数据、协程、循环引用、以空值为键。嵌套和表项有上限；整包编码也有上限。数字见 [可用资源](resources.md)。

## 6. 软件定时器

软件定时器到期后 **先投进事件队列**，再在循环里调回调。不是独立的操作系统线程。

```lua
-- 伪码
登记一次到期(毫秒, 回调)
登记周期到期(毫秒, 回调)
```

当前最多 **8** 路。回调同样必须短。周期打点如果只是「到点投递一条消息」，比再开一条协程更省槽位；需要在到点后做一长串业务，仍应投递给工作协程。

对齐钟面（每天 10:15、每小时整点）不是软件定时器的职责，那是日程模块，见 [`cron`](../api/module/cron.md)。

## 7. 三种「等一会儿」

这是最容易用错的地方。三者都叫「延时」，调度含义完全不同。

| 种类 | 谁在等 | 其它 Lua 协程 | 其它系统线程 | 典型用途 |
| --- | --- | --- | --- | --- |
| 让出延时 | 当前协程把 CPU 还给调度 | **能跑** | 能跑 | 日常等待、空闲、配合低功耗 |
| 整线程睡眠 | 整条脚本引擎线程挂起 | **全停** | 能跑（含喂狗监控） | 短时序必须准、不准被其它协程插队 |
| CPU 忙等 | 当前核空转 | 全停 | **也调度不了** | 仅极短脚线；到毫秒必须换掉 |

```lua
-- 伪码：日常
循环:
    采样()
    让出(1000)

-- 伪码：不要当日常等待
整线程睡眠(1000)     -- 这一秒里 MQTT 回调、其它任务都走不到

-- 伪码：更不要
忙等(1_000_000)      -- 微秒空转拉长到秒级，看门狗可能喂不上
```

日常周期、等网、多任务并存，默认用让出。整线程睡眠只留给「中间不能插入其它 Lua」的短时序。忙等只留给几十到几百微秒的脚线。

## 8. 推荐骨架

长期业务常见写法：一条工作协程专门收消息，入口协程负责保活。

```lua
-- 伪码
启动任务:
    循环:
        成功, 事件 = 等待信箱("events")
        若 成功:
            按事件类型处理()     -- 业务只放这里

注册外设 / 网络回调:
    投递信箱("events", 摘要)
    立即返回

循环:                         -- 入口保活，并给调度让出点
    让出(较长一段时间)
```

最小入门可以更短：入口自己循环打印再让出。见 [started/hello](../../../examples/nt26/started/hello)、[started/task](../../../examples/nt26/started/task)。

## 9. 写脚本时的调度纪律

1. **先有人等，再注册回调。** 否则头几条广播信箱会丢。
2. **回调只投递。** 编解码、写盘、组 MQTT 放进工作协程。
3. **入口或至少一条任务必须周期性让出。**
4. **不要在回调、定时器回调、连接前回调里让出或同步阻塞。**
5. **主题名短且唯一。** 超长截断会撞车。
6. **队列要先创建。** 信箱不用创建，但没有积压。
7. **对象要被脚本持有。** 网络客户端、打开的脚，只存在局部临时变量里可能被回收后断连或关口。
8. **布尔开关写真/假。** 走布尔语义的参数里，数字 `0` 往往是「真」。电平、方向不要传 `0`/`1` 去碰运气。
9. **事件队列满先查消费侧。** 少在回调里发大表，加快工作协程取出。
