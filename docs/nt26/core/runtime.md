## 1. 总流程

```
上电 / 复位
    │
    ▼
固件完成底软初始化（驻网、AT、存储等可并行）
    │
    ▼
选定要跑的脚本（当前版本双槽切换未启用，见第 2 节）
    │
    ▼
（可选）等首次网络同步结束，再按清单里的延迟秒数等候
    │
    ▼
读取该槽清单：入口文件、用户模块名、是否启用
    │
    ▼
创建脚本虚拟机（带堆上限）
    │
    ▼
打开允许的标准库，登记平台模块和用户模块加载器
    │
    ▼
把入口源码编译进一条独立协程并启动
    │
    ▼
进入调度循环：直到没有可跑的任务且没有待处理事件
```

清单里可以关掉脚本（入口为空或不启用）。关掉则不建虚拟机，设备仍可当纯 AT / RTU 用。

延迟启动的目的，是让驻网、配置落盘等先稳定。具体秒数写在包的选项里，不是脚本自己 `require` 出来的。

## 2. 脚本副本：A / B 两槽

底层按 **A、B 两槽** 设计：一份在跑，另一份可以备着；开机只跑当前引导包，两槽不会各开一个虚拟机。

```
        ┌──────────┐     ┌──────────┐
  设计  │  槽 A     │     │  槽 B     │
        └────┬─────┘     └────┬─────┘
             │                │
             └───────┬────────┘
                     ▼
              当前引导包（一次只跑一份）
                     │
                     ▼
                 脚本虚拟机
```

**当前 NT26（含 NT26 PRO）产品配置未启用双槽切换。** 本版本内部可用空间偏紧（脚本还要和内部文件共用约 220 KB），两份完整包会把配额吃光。因此现在不要按「写到空闲槽 → 试运行 → 确认 / 回滚」来规划升级，把设备当成 **一份正在跑的脚本** 来部署即可。

切槽是底层能力，不是这一版的产品路径。日后在内部空间更大的 **8+8** 版本，或 **CAT4** 版本上，才可能打开。打开之前：

- 不要调用脚本侧切槽 / 回滚接口（名字即使挂在模块表上，也未作为产品交付）
- 不要把 AT 选槽、试运行、回滚当成已开通的业务
- 查询当前版本、清单仍然可用

| 模式 | 设计含义 | 当前版本 |
| --- | --- | --- |
| 正式 | 已确认路径，开机跑当前槽 | 实际在用的就是这一份 |
| 试运行 | 新包先跑一段时间，失败可回到旧槽 | **未启用**，不要按这条路径写工具或脚本 |

两槽的文件若都落盘，会一起占内部共享配额（见 [可用资源](resources.md)）。当前既然未切槽，就不要长期留第二份完整包。细节见 [`script` API](../api/module/script.md)。

部署入口：[脚本 AT](../at/script.md)、配套下载工具。

## 3. 虚拟机怎么建起来

可以把它想成三步，而不必关心分配器名字。

```lua
-- 伪码
堆 = 创建有上限的脚本堆()          -- 当前固件默认约 700 KB，见资源篇
虚拟机 = 新建虚拟机(堆)
打开标准库(虚拟机)                 -- 无 io / os，有 package
登记平台模块(虚拟机)               -- require("gpio") 这一类
登记用户模块加载器(虚拟机)         -- require("你的模块名") 时再读盘
入口协程 = 新建协程(虚拟机)
编译(入口协程, 入口源码)
启动(入口协程)
进入调度循环(虚拟机)
```

源码在编译进虚拟机之后，加载侧占用的临时缓冲会放开。用户模块默认 **不预编译、不常驻** 在加载缓冲里：第一次 `require` 才读盘、编译、立刻丢掉源码缓冲，字节码留在 Lua 堆上。

平台模块同样是按需装入虚拟机（启动即需要的少数模块会提前装）。所以「工程里 require 了十个平台模块」不会在开机瞬间把十份实现都展开；真正执行到 `require` 才占堆。

## 4. 入口协程

入口脚本 **本身就是一条协程**。顶层可以直接让出、等消息，不必再包一层「启动任务」。

```lua
-- 伪码：合法的入口形态
循环:
    干活()
    让出(一段时间)

-- 伪码：也常见——入口再开工作任务，自己只负责保活
启动任务(工作循环)
循环:
    让出(较长一段时间)
```

| 事实 | 含义 |
| --- | --- |
| 入口顶层算任务协程 | 顶层可以等、可以让出 |
| 再开任务会占槽位 | 连入口第一次让出所占用的槽，一共大约 16 条，见资源篇 |
| 入口 `return` 只结束自己 | 其它已启动且还在等事件的任务可以继续 |
| 入口若写从不让出的死循环 | 调度循环插不进别的任务和回调，整台脚本饿死 |

编译失败（语法错）发生在「启动入口协程」之前，调度循环不会开始。运行期抛错会终止当前这条路径，并按固件策略上报脚本错误。

## 5. 用户模块何时真正装入

```
require("led")
    │
    ▼
已加载过？ ──是──► 返回第一次的那张表（单次加载）
    │否
    ▼
加载器按模块名从当前引导包读源码
    │
    ▼
编译并执行模块文件（末尾应返回一张表）
    │
    ▼
释放源码缓冲，表留在虚拟机里
```

因此：

- 模块文件要在清单里，名字与 `require` 一致。
- 模块里的顶层代码在 **第一次 require 时** 执行一次，适合做初始化表，不适合在顶层写「永远不让出的死循环」。
- 平台名不要再用同名用户文件去抢。

## 6. 脚本什么时候算结束

调度循环在「没有可唤醒的任务、也没有待派发事件」时可以停。实践上：

| 写法 | 结果 |
| --- | --- |
| 入口跑完就 `return`，也没开长期任务 | 生命周期很快结束 |
| 开了任务，但大家都 return 了 | 同样结束 |
| 留一条「永远让出再醒来」的循环 | 长期业务，推荐 |
| 注册了外设回调，但所有协程都结束了 | 事件可能仍会进队，却没有业务协程处理 |

长期业务请至少留一条会让出的循环。虚拟机退出时，任务、等待、信箱回调、队列、软件定时器一并拆掉；内部存储里的文件还在。

改脚本、换槽、复位之后才会按新的引导包再建虚拟机。热更新正在跑的入口文件不是常规路径。

## 7. 引擎线程和整机其它工作

```
┌──────────────────────────────────────────┐
│ 脚本引擎线程                              │
│  虚拟机 + 调度循环 + 全部 Lua 回调         │
└──────────────────────────────────────────┘
          ║ 同时存在，不是同一条
┌─────────╨────────────────────────────────┐
│ 驻网 / AT / USB / 看门狗监控 等            │
└──────────────────────────────────────────┘
```

- 脚本里的「多任务」是虚拟机内部的协程，**不是**操作系统抢占线程。
- 引擎线程被按停时（整线程睡眠、或 CPU 忙等），Lua 回调和协程都不跑；其它线程仍可能在工作。
- 外设和网络的底层收包发生在各自路径，但 **Lua 回调一定回到调度循环再执行**。

三种「等一会儿」的差别见 [消息和调度](schedule.md)。

## 8. 失败时你会看到什么

常见分界：

| 阶段 | 典型现象 |
| --- | --- |
| 清单 / 文件不完整 | 不启动脚本，或启动后立刻失败 |
| 入口编译失败 | 语法或加载错误，调度循环未开始 |
| 堆不够 | 创建虚拟机或运行中分配失败 |
| 运行期未捕获错误 | 上报脚本错误 |
| 共享配额满 | 新包或内部文件写不进去，已在跑的虚拟机不一定马上停 |

查询当前这份脚本的版本即可。部署与擦槽用工具或 AT。当前版本不要按试运行 / 切槽来排故障。
